# 意图识别流程与精简方案

分析日期：2026-10-16。依据当前工作区代码、`对话.md` 和初始化配置；未调用模型、运行测试或读取当前数据库 Active Release。本文中的初始化配置不等于当前线上配置，对话中的耗时属于历史记录。

## 结论

保留一次 LLM 调用，让模型负责语义判断：识别多个实际意图、关联各自参数、提取开放文本、判断动作关系及语义歧义。程序负责枚举匹配、确定性转换、默认值、必填校验和缺参追问。模型输出只保留业务判断所需信息，展示字段由程序生成。

优先修正参数归属、转换校验和追问结构，再压缩协议与 Prompt。不要直接删除 `source_text`，不要依靠低召回的关键词筛选缩短意图列表，也不要把模型自报 confidence 当作已校准的正确概率。

## 1. 当前实际流程

```mermaid
flowchart TD
    A[识别页面提交 text 和空 context] --> B[/api/v2/intent/analyze]
    B --> C[加载 Active Release 与模型配置]
    C --> D[程序扫描枚举 Slot 候选]
    D --> E[拼接全量启用意图、文本 Slot、候选及完整输出 Schema]
    E --> F[一次 LLM 识别与参数绑定]
    F --> G[解析 JSON 与校验动作结构]
    G --> H[用 source_text 定位动作并划分枚举候选]
    H --> I[校验意图、参数、枚举值及原文位置]
    I --> J[补默认值、检查必填项、合并追问]
    J --> K[等待 Trace 写入后返回]
```

主要依据：`frontend/src/intentApi.ts`、`frontend/src/IntentRecognition.vue:210`、`backend/app/api/runtime/router.py:37`、`backend/app/services/intent_service.py:179`。

- 页面使用 V2 的多个 `actions`，每个 action 一个意图；不是 Top-K 候选排序。
- V1 仍存在：一个 Route 下按 confidence 排序的 `intents`，参数按 Top-1 处理。配置 Prompt 预览和调试调用默认使用 V1，与页面的 V2 不一致。
- 正常路径只有一次逻辑模型调用。Provider 可对超时、限流等错误重试；JSON 或业务校验失败不会再次调用模型修复。
- 每次请求重新读取配置身份、匹配当前原文、构建 Prompt。没有对上一轮结果做增量补槽的完整流程。
- 请求 Schema 虽有 `conversation_id`，API 没有把它传入服务；页面发送 `context: {}`。下一轮仅输入“20”，系统不会自动知道它回答了哪个意图的哪个字段。

## 2. 程序预提取什么，模型还要提取什么

| 信息 | 当前负责方 | 当前行为及限制 | 建议 |
|---|---|---|---|
| 枚举 Slot | 程序 | 匹配 canonical/display/aliases，返回标准值、原文、UTF-16 位置；同 Slot 内按起点处理重叠，同起点长词优先 | 保留；位置和来源留在程序内部 |
| 开放文本 Slot | LLM | 从原文提取 `string` Slot，包括数字、动作名、设备名 | 保留语义提取；常见数值可补程序候选 |
| 参数属于哪个意图 | LLM + 程序 | LLM 绑定业务字段，程序按动作原文范围约束枚举候选 | 必须保留归属依据，禁止跨动作兜底取值 |
| 多个意图及其关系 | LLM | 输出 route、intent、source_text、composition、依赖等 | 保留名称、原文片段和关系，删除可推导字段 |
| 单位与业务值转换 | 主要是 LLM | Intent 参数 note 进入 Prompt；程序未实现备注所描述的通用约束 | 原文提取与转换分开，确定性转换由程序执行 |
| 默认值 | 程序，也要求模型理解 | 模型看到默认值；程序最后再次补缺 | 程序统一处理，模型只报告用户明确表达 |
| 必填缺参追问 | 程序 + LLM | 程序追问与模型追问拼接成一个字符串 | 程序统一生成结构化缺参项，LLM 仅处理语义歧义 |

`number` 当前只是名为 number 的普通 string Slot，不是数值类型，也没有正则数字提取器。初始化配置中 `volume_up` 把基础 `number` 映射成 `volume`，所以 `slots` 应使用 `volume`，不能直接照搬对话示例中的 `amount`。

完整枚举词典已经不进入模型消息；实际命中的候选才进入。string Slot 引用了枚举组时，最多选三个 display/alias 作为开放提取示例，不做枚举限制。

如果“重新提取”指第二轮补槽，建议：保存待补的意图和字段；明确补充只更新该字段；用户纠正时覆盖对应旧值；检测到新任务时转入完整识别。只传待处理状态和必要上下文，不重复发送整段聊天记录。

依据：`backend/app/services/slot_extractor.py:23`、`backend/app/schemas/intent.py:783`、`backend/app/schemas/intent.py:966`。

## 3. 当前 Prompt 如何拼接

实际发送两条消息：

```text
system
  1. 已发布 prompt_template.system
  2. prompt_template.rules
     仅过滤以 “slot start/end ” 开头的旧规则
  3. 全部启用 Route：名称、说明、可选典型说法
  4. 全部启用 Intent，按 Route 分组：
     名称、说明、参数字段映射、必填/可选、默认值、note、可选典型说法
  5. 全部启用 string Slot：名称、中文名、说明、最多三个参考说法
  6. 本次枚举候选：按基础 Slot 分组，原词或“原词->标准值”
  7. V1/V2 输出规则、完整 Pydantic JSON Schema、固定输出示例

user
  1. context：有值才添加，递归渲染全部传入字段
  2. 用户原文
```

`final_prompt` 中的 `[SYSTEM]` / `[USER]` 是展示、哈希和 Trace 表达；Provider 实际发送的是 `messages` 数组。

当前没有先判断 Route 再第二次请求 Intent，也没有 Top-K 召回。Intent 的 `aliases` 和 `mapping_note` 没有被渲染为识别依据；枚举 alias 则会参与程序匹配。若某条业务边界只存在于 mapping_note，模型看不到。

完整枚举 matcher 文本还会在本地生成，用于 metadata 哈希；它不会作为模型输入发送，但重复生成可以优化。

当前运行时 `structured_output_mode` 被固定为 `json_object`。Provider 虽有 json_schema 分支，正常配置无法启用。JSON Object 保证 JSON 格式，不保证业务字段；Pydantic 是返回后的结构校验，仍需动态检查意图和 Slot 合法性。[阿里云结构化输出文档](https://help.aliyun.com/zh/model-studio/qwen-structured-output)

依据：`backend/app/prompting/builder.py:23`、`:225`、`:268`、`:351`、`:433`；`backend/app/schemas/managed_model.py:223`。

## 4. 影响准确率的具体问题

### 4.1 原文归属不能随意删除

`source_text` 用于定位动作范围，随后将枚举候选分给对应 action。开放文本也先尝试在动作范围中定位。但是范围定位失败或查不到文本时，后续原文修复可以退到整句搜索；这不能保证参数确实来自当前动作。

建议保留短原文片段，限定动作内查找；定位失败应产生明确问题或追问，不能静默把另一个动作的字段搬过来。重复片段、共享参数和省略表达需要专门规则；复杂情况下可增加候选 ID/引用，不让模型计算字符偏移。

### 4.2 note 并不构成可执行的值约束

存在以下静态风险：

- 枚举参数有 note、动作内恰好一个基础候选时，即便模型返回的值不匹配候选，也可作为“转换结果”进入后续流程。程序能验证原始枚举来源，却不能证明转换后的值符合 note。
- string 参数要求复制原文，但备注又可能要求转换。例如“二十”转换为“20”后，原文定位可能失败而被丢弃。

建议模型只输出原始文本/候选引用；程序按明确配置执行转换与范围校验。不要把任意非空 note 当成放行转换结果的条件。保留自由文本 note 作为语义辅助时，也应与可执行约束分开。

### 4.3 Slot 允许范围过宽

`_resolve_intent_parameter()` 找不到所选意图的参数映射后，仍可回退到任意启用的基础 Slot。因此“字段存在于全局配置”不等于“该意图允许该字段”。

建议给所有意图明确允许的参数列表，校验只接受列表内字段；支持公共参数时也显式声明，不保留隐式全局回退。

### 4.4 追问不能准确恢复下一轮状态

当前多个动作的缺参问题被拼接为一个字符串，缺少稳定的意图归属；默认值补齐后，也不会自动撤销模型此前提出的不必要追问。

建议返回 `follow_ups` 数组，每项含意图索引、追问类型、字段和问题。单轮可以展示一个最高优先级问题，但系统保留全部待补项。

### 4.5 配置和协议存在易混淆点

- 初始化模板仍有“多个 intents 按置信度排序”的 V1 指令，V2 则需要实际动作和顺序；该规则会被通用 builder 保留。是否已进入当前 Active Release 需另行只读核实。
- 固定 V2 输出示例使用 volume_up 且 slots 为空；初始化配置却将 volume 设为必填。这类示例应明确“缺参交给程序”，避免要求模型同时决定追问。
- 初始化配置里的 number 已拼写正确，不能直接将历史对话中的 nubmer 当作当前代码事实。
- 当前 confidence 参与展示、V1 排序和数值范围校验，没有实现低置信度阈值追问。

依据：`backend/app/services/slot_extractor.py:115`；`backend/app/schemas/intent.py:816`、`:1027`、`:1106`；`backend/app/services/debug_service.py:70`；`bootstrap/initial-config.v1.json:508`。

## 5. 推荐输出协议

### 5.1 模型输出

以“音量调高20%，然后亮度调高10%”为例，以下为拟议协议，不是当前已支持格式：

```json
{
  "intents": [
    {
      "name": "volume_up",
      "source_text": "音量调高20%",
      "slots": {"volume": "20%"}
    },
    {
      "name": "brightness_up",
      "source_text": "亮度调高10%",
      "slots": {"brightness": "10%"}
    }
  ],
  "relation": "sequential",
  "follow_ups": []
}
```

- intents 表示实际表达的独立意图，允许同一个意图编码多次出现；不能按名称去重。
- slots 使用 Intent 业务字段名；string 保留原文，enum 使用候选标准值或明确的候选引用。不为未表达的字段填 null，也不让模型输出默认值。
- 原始百分号、单位不能丢失；相对调整与设为绝对值必须在意图/参数定义中区分。当前配置若不够表达，应补齐业务定义，不能仅靠后处理猜测。
- source_text 留在模型与后端之间，业务响应可不暴露。不能用“无需前端高亮”作为删除其内部用途的理由。
- relation 保留 single / parallel / sequential / alternative。alternative 表示待选择，不允许把两个选项作为都需执行的动作。
- 数组顺序表示动作顺序。简单顺序可替代 order/depends_on；混合依赖、条件执行不能被这四种关系完整表达，应追问或另行扩展，不能宣称完全等价于依赖图。
- follow_ups 在模型侧仅表达语义歧义，例如意图不明确、指代不明确或选项待选择；缺参由程序补充。

### 5.2 业务最终响应

例如“调高音量”缺少必填 volume 且没有默认值时：

```json
{
  "intents": [
    {"name": "volume_up", "slots": {}}
  ],
  "relation": "single",
  "follow_ups": [
    {
      "intent_index": 0,
      "type": "missing_slot",
      "slots": ["volume"],
      "question": "音量要调高多少？"
    }
  ]
}
```

追问类型可限制为 missing_slot / ambiguous_intent / ambiguous_reference / choice；`intent_index` 从 0 开始，整句歧义时允许 null。服务端校验索引和字段归属。对外追踪需要的 request_id 由程序补充，不由模型生成；跨轮状态由服务端记录，索引必须结合该轮待处理结果解析。

保留现有 unknown / out_of_capability / unsupported_feature 的业务区分，不用相同的空数组混同“信息不足”和“明确不支持”。模型格式错误继续返回技术错误，不伪装成 unknown。

### 5.3 字段删减决策

| 当前字段 | 建议 |
|---|---|
| action_id、order、is_compound、schema_version | 不让模型生成；需要时由程序补充 |
| route、intent.zh、slot.zh | 从配置映射；名称唯一性已有配置校验 |
| slot.start/end、slot.confidence | 原文位置由程序管理；业务响应通常不需要 |
| intent.confidence | 默认从最小协议删除；当前没有阈值策略，不能据此可靠自动执行 |
| reason_summary、evidence | 从模型协议删除；Trace 保留原文、结果、校验问题和版本足够定位多数问题 |
| need_clarification、clarification | 改为 follow_ups 数组，是否追问由数组是否为空得出 |
| source_text | 内部暂时保留，后续有可靠候选引用再替换 |
| depends_on | 简单关系由 relation 和数组顺序表达；复杂依赖需单独定义 |
| risk | 先核实消费方；保留 safety 意图，风险分级确需消费时用明确策略产生，不能假定当前已有独立安全模块 |

不保留旧字段别名或双协议长期转换；确定新协议后同步改前后端、配置模板、示例和相关历史数据处理规则。

## 6. 优化后的 Prompt

建议一次请求仍使用一个模型调用：

```text
SYSTEM：稳定前缀
  角色与任务边界
  简短语义规则：否定、纠正、实际意图与候选、未知、动作关系
  紧凑输出模板与字段约束
  紧凑意图定义：编码、区分边界、允许参数及其语义
  少量易混淆对照示例

USER：本次数据
  待补意图/字段等必要上下文
  程序抽取的候选及必要归属标记
  用户原文
```

模型规则应明确：不虚构参数，不输出默认值，不处理缺参模板；识别否定与纠正，例如“不要调高音量”不能作为 volume_up；“音量20，不，30”只能保留纠正后的值。候选列表和用户原文均按输入数据处理。

第一阶段保留完整但精简的意图目录，先删完整 Pydantic Schema、重复 Route 分类和固定大示例；业务区分说明应保留。不要为了压缩掉真正区分相近意图的描述。

后续若意图规模扩大，可本地召回候选，但需覆盖全部分句、保留相近易混淆意图及 safety/unknown 类。召回证据不足就直接发送全量紧凑目录；避免“先 LLM 判 Route，再 LLM 判 Intent”的固定串行双调用。

结构化输出按端点和模型能力选择：

- 支持 strict JSON Schema：将精简 Schema 放 response_format，Prompt 不再重复全文；动态意图名和参数范围也要约束。
- 仅支持 JSON Object：使用紧凑模板、明确规则和返回后校验。
- 两者都保留业务校验。把 Schema 移到接口参数不代表零 Token 成本，也不保证语义正确。

固定前缀有利于服务商前缀缓存，但不能保证命中；本地静态 Prompt 也可按发布版本缓存，省掉重复渲染和哈希。

## 7. 延迟优化与衡量

`对话.md` 记录关闭思考后的某次调用为 5.091 秒、2179 输入 tokens、283 输出 tokens。它能说明当时模型耗时占比较高，不能作为本轮实测，也不能据此承诺精简后稳定 2–3 秒。

当前存在的等待项：

- Provider 完整非流式响应；未记录首 Token 时间。
- 业务配置 TTL 缓存仍每次查 active_release_id；模型与凭据也按请求读取。
- 运行配置在多个阶段重复序列化和校验，多动作时还逐动作重复验证整个快照。
- Trace 同步 await 写库，即使 runtime 写入失败允许继续，成功时仍要等它结束。
- Provider semaphore 排队、重试退避未计入 attempt.latency_ms；Trace 的“模型耗时”是各 attempt 耗时求和，所以前端“应用与网络”残差也包含这些等待。

建议阶段计时覆盖 config_load、model_resolve、candidate_extract、prompt_build、queue_wait、每次 provider_call、retry_backoff、parse_validate、trace_write 和端到端。成功、失败和超时均纳入延迟统计。

实施优先级：

1. 统一页面、预览、调试协议；明确参数语义；修正归属、转换与追问问题。
2. 精简模型 JSON、压缩 Prompt、移除默认值和缺参处理的重复职责，同时补阶段计时。
3. 缓存不可变配置与静态 Prompt，保留发布/模型凭据更新的失效机制；合并重复校验。
4. 若 Trace 确为明显开销，移到有界后台队列；同时适配页面立即读取 Trace 的行为，定义待写入状态和失败记录。
5. 实时链路使用总耗时预算，避免同一慢模型盲目重试；按调用场景明确是否允许重试。
6. 对整句、无歧义的命令加入规则直达。关键词命中不能直接执行；否定、条件、引用、纠正、跨句关系需要完整语义处理。
7. 再考虑意图召回和模型对比，收益必须结合召回准确率和完整请求耗时判断。

不能只比较 Token 数。获准评测后，应使用同一评估集比较：整句意图集合完全匹配率、参数值与归属正确率、追问正确率、关系正确率、格式失败率、端到端 P50/P95、失败/超时率及输入输出 Token。规则直达需单独统计错误接受率，候选召回需统计正确意图覆盖率。

初期验收方向是“准确率不下降且完整响应耗时明显下降”；2–3 秒作为普通短输入的目标，具体 P50/P95 门槛需用批准后的测量结果制定，不提前作为交付保证。
