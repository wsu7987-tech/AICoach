# 10 契约不变量与验收样例（v1.2.5 新增）

> 目的：把“为什么前几个 Task 反复被 Review 打回”的根因固化为**可执行的验收依据**。Review 与自测都以本文为准；与实现或其他文档冲突时，以本文 + `docs/03/06/07` 为准，并把冲突记入执行报告。

## 1. 各路由的合法 / 非法输出

固定字段：`route`、`intents[]`、`slots[]`、`risk`（必须出现，可为 null）、`need_clarification`、`clarification`。

| 场景 | 输入输出要点 | 结论 |
|---|---|---|
| training Route-only | `route=training_business, intents=[], slots=[], risk=null, need_clarification=false, clarification=null` | ✅ 合法；Trace 记录 `INTENTS_EMPTY` |
| training 带 Intent/Slot | `intents=[start_training], slots=[exercise]` | ✅ 按相同规则识别和返回；计划中的结果匹配验证只比较 Route |
| training 要追问 | 模型给 `need_clarification=true, clarification="练哪个部位？"` | ✅ 与其他 Route 一样保留追问 |
| 非训练正常 | `route=information_query, intents=[query_progress]` | ✅ |
| 任意 Route 空 intents | `intents=[]` | ✅ 请求成功；Trace 记录 `INTENTS_EMPTY` |
| safety + risk | `route=safety, risk={type,zh,level}` | ✅（不强制 safety 必带 risk，也不做关键词推断） |
| `need_clarification=true` 且 clarification 为 null/空串 | | ❌ `MODEL_OUTPUT_SCHEMA_ERROR` |
| 任意 Route `need_clarification=false` 且 clarification 非空 | | ❌ `MODEL_OUTPUT_SCHEMA_ERROR` |
| route 不是固定 7 个之一 | | ❌ `MODEL_OUTPUT_SCHEMA_ERROR` |
| intent 不在当前 Snapshot，或其所属 route ≠ 返回 route | | ❌ `MODEL_OUTPUT_SCHEMA_ERROR` |
| confidence 不在 0..1 | | ❌ `MODEL_OUTPUT_SCHEMA_ERROR` |
| `risk` 缺失（字段不存在） | | ❌ `MODEL_OUTPUT_SCHEMA_ERROR`（null 合法，缺失非法） |
| Runtime 响应含 prompt/raw/reason/evidence/model params | | ❌ 响应模型 `extra=forbid`，测试断言字段集合恰好等于 Contract |
| 基础设施/Provider 失败 | 超时、429、5xx、非 JSON | ❌ 对应 error_code，**不得**伪装成 `route=unknown` |

> 若现有实现与上表不一致，以本表为准修正；如修正会破坏已通过测试的语义，记入报告请产品/研发决策，不要自行选边。

## 2. Slot span 规则与边界样例

UTF-16 code-unit，`[start,end)`。

| text | slot value | 正确 span | 说明 |
|---|---|---|---|
| `我要做深蹲` | 深蹲 | [3,5) | 基本情形 |
| `😀我要做深蹲` | 深蹲 | [5,7) | emoji 占 2 个 code unit |
| `深蹲深蹲` | 深蹲 | 模型给错下标 → **丢弃** | value 出现多次，歧义 |
| `我要练胸` | 深蹲 | 模型给任意下标 → **丢弃** | value 不存在 |
| `我要做深蹲` | 深蹲 | 模型给 [0,2) → **重算为 [3,5)** | value 唯一 |

丢弃时：请求仍成功，`validation_json` 记录 `SLOT_SPAN_INVALID`（含原 slot）。这三类（重算 / value 不存在 / 多处歧义）各一条独立测试。

## 3. Snapshot 校验不得被“已构造的实例”绕过

Pydantic v2 默认 `model_validate(instance)` **不会重新校验**已有实例。因此：

- 校验入口（`validate_snapshot` / Publish / PromptBuilder 入口）必须基于 **dict 重新解析**（`Model.model_validate(snapshot.model_dump())`），或模型配置 `revalidate_instances='always'`，二选一并写进测试；
- Snapshot 构造后被改动（删一个 route、disable 一个 route、新增第 8 个 route、intent 指向不存在的 route）必须被校验函数拒绝；
- Snapshot 对象在校验通过后应冻结（`frozen=True` 或等价）或仅以只读视图传递。

## 4. hash 语义

- `config_snapshot_hash`、`release_fingerprint` **都不唯一**（回退会产生内容相同的新 Release）。数据库只允许普通索引。
- 必须有测试：同一 Snapshot 连续发布两次 → 两个 Release 行并存，hash 相同，`release_id` 不同。
- `model_config_hash` 只基于不可变 runtime payload，排除 id/name/enabled/version/时间戳。

## 5. `/ready` 判定

- 通过条件：进程可服务 + DB 可连 + **metadata 推导的**必需表与列齐全（一次查询）。
- 不检查：Active Release、default Model Config、Provider 可达性。
- 必须有测试：① 空库 migration 后 ready；② 删一张表 → not ready；③ 删一列 → not ready（不能只查表名）；④ 无 Active Release 仍 ready 且 `runtime_config_ready=false`。

## 7. 格式与门禁

Task 提交前必须全部通过，并把**实际命令输出**贴进执行报告（不是只写“通过”）：

```text
uv run --locked --extra dev ruff check .
uv run --locked --extra dev ruff format --check .
uv run --locked --extra dev pytest -q -rs
```

`skip` 必须逐条解释；不允许为让门禁通过而放宽测试或加 `noqa`（确需时在报告里写明原因）。
