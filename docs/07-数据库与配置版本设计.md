# 07 数据库与配置版本设计

## 1. 原则

一期选择**少表 + 不可变 Snapshot**，避免为配置中心建立大量关系表。MySQL 8 独立资源，`utf8mb4`。

## 2. 核心表

### config_draft

- id（一期可 singleton）
- schema_version
- draft_json
- updated_by
- updated_at

Draft 包含 routes/intents/slots/enums/examples/prompt_template。

### model_config

- id
- name/version
- provider/model
- base_url
- params_json
- timeout_seconds
- max_retries（首次调用之外允许的最大重试次数；单次 execution 最多 1 + max_retries 个 LLMAttempt）
- max_concurrency
- structured_output_mode
- credential_ref（仅逻辑引用名，指向后端环境变量/K8s Secret，不存真实 Key）
- model_config_hash（SHA256(canonical immutable runtime config)，创建版本时计算并不可变）。Hash payload **只包含实际影响模型调用的非 Secret 字段**：`provider/model/base_url/params_json/timeout_seconds/max_retries/max_concurrency/structured_output_mode/credential_ref` 的逻辑引用值；排除 `id/name/version/enabled/immutable_from_at/created_at/updated_at` 等生命周期/展示元数据。
- enabled
- immutable_from_at / created_at

Secret/API Key 不存 DB；只存 Secret 名称/环境引用或由统一 settings 获取。

### config_release

- id/version
- snapshot_json（仅 Business Config Snapshot）
- config_snapshot_hash（SHA256(canonical business snapshot)）
- default_model_config_id
- model_config_hash（发布时冻结的副本）
- release_fingerprint（SHA256(config_snapshot_hash + default_model_config_id + model_config_hash)）
- **`config_snapshot_hash` 与 `release_fingerprint` 都不是唯一键：** 回退 = 把历史 Snapshot 复制为新 Draft 再发布新 Release，内容相同则 hash/fingerprint 相同。允许建普通索引，禁止 UNIQUE 约束。身份靠 `release_id`/`version`。（TASK-002 实测曾因 UNIQUE 导致回退发布失败，已移除。）
- note
- created_by/created_at

历史行不可修改。

### runtime_state

singleton：

- active_release_id
- updated_at

发布事务：先写 release，再原子更新 runtime_state。

### intent_request_trace

请求级：

- trace_id unique
- request_id indexed
- parent_trace_id nullable
- source/input/context
- release_id / config_snapshot_hash / release_fingerprint
- effective_model_config_id / model_config_hash
- model_config_snapshot_json
- final_route/final_result_json
- reason_summary/evidence_json
- validation_json/timeline_json
- latency/token/retry/status/error
- created_at

### llm_call_trace

Attempt 级：

- trace_id
- attempt_no
- provider/model
- model_params_json
- final_prompt / prompt_hash
- raw_request_json / raw_response_json
- final_prompt_truncated / raw_request_truncated / raw_response_truncated（bool）
- provider_request_id
- provider_model_version
- system_fingerprint
- finish_reason
- parsed_result_json
- token/latency/status/error
- created_at

唯一键：`(trace_id, attempt_no)`。

### evaluation_dataset

- id/name/version/source_filename/hash
- normalized_cases_json
- created_at

### evaluation_run

- id/dataset_id
- dataset_hash
- release_id / config_snapshot_hash / release_fingerprint
- effective_model_config_id / model_config_hash / model_config_snapshot_json
- repeat_count / worker_concurrency
- status/progress
- claimed_by/heartbeat_at
- error
- created_at/started_at/finished_at

### evaluation_case_result

- run_id
- case_id
- repeat_index
- expected_json/actual_json
- passed/error_type/error_message
- request_id/trace_id
- latency

唯一键：`(run_id, case_id, repeat_index)`。`trace_id` 是可过期的逻辑引用：不得使用会阻止 Trace cleanup 的 RESTRICT FK，也不得因 Trace 删除级联删除评测结果；可使用普通索引字符串或可置空/兼容删除的关系。`intent_request_trace.parent_trace_id` 同理不得阻止父 Trace 到期清理。

## 3. Release 发布

```text
Draft validate
-> canonicalize JSON
-> attach default_model_config_id（由发布请求显式传入，必填；必须 enabled；计算 model_config_hash / release_fingerprint）
-> create immutable Release
-> hash
-> transaction switch runtime_state.active_release_id
-> Runtime cache eventually refreshes within TTL
```

## 4. 回退

```text
historical release
-> create draft from snapshot
-> optional edit
-> publish new release
```

不修改旧 Release，也不把 Active 指针直接切回旧行而跳过审计。

## 5. Bootstrap

`bootstrap/initial-config.v1.json` 仅用于首次创建 Draft。它不是运行时硬编码来源，也不会自动发布生产 Release。Bootstrap 顶层字段必须严格等于 Business Config Draft Schema：`schema_version/routes/intents/slots/enums/examples/prompt_template`；Route Contract/审批状态等元数据不得混入 Draft/Snapshot/hash。

生产首次上线步骤：

1. migration
2. import bootstrap to draft
3. 研发确认业务配置
4. 创建 Model Config
5. validate
6. publish first Release
7. `/api/admin/status/summary.runtime_config_ready` 变为 true；`/ready` 在 DB/schema 可服务后即应为 ready，不等待首个 Release

## 6. 数据体量

一期 Raw Prompt/Response 直接 MySQL JSON/TEXT 存储。后续若体量增长，再评估对象存储/日志平台；一期不预引入。

## 7. Model Config Disable / Delete Contract

- Active Release 引用中的 Model Config 不允许 disable。
- Running Evaluation 已冻结的 Model Config 后续即使 disable，也不影响该 Run。
- disabled Model Config 不允许被新的 Release、Debug Override、Evaluation Override 选择。
- 历史 Trace/Replay 继续依赖保存的 immutable Model Config snapshot。
- 已被 Release/Trace/Evaluation 引用的 Model Config 一期禁止物理删除。
- `credential_ref` 生命周期与 Model Config 独立；disable 不自动删除 Secret。

## 8. Trace 索引与生命周期

至少为 Trace/Run 查询建立适合的索引：`created_at`、`status`、`final_route`、`release_id`、`effective_model_config_id`，并根据实际 SQL 使用组合索引。

Trace 支持：
- `TRACE_RETENTION_DAYS`；
- `TRACE_RAW_MAX_BYTES`；
- raw 字段截断标记；
- request + attempts 级联清理；
- cleanup command/CronJob。

### Evaluation 关联 Trace 的保留
- 与 Evaluation Run 关联的 Trace（`evaluation_case_result.trace_id`）使用独立配置 `EVAL_TRACE_RETENTION_DAYS`（建议默认 ≥ 90 天，且不小于 `TRACE_RETENTION_DAYS`），其余 Trace 使用 `TRACE_RETENTION_DAYS`。
- Trace 被清理后，`evaluation_case_result` 的 expected/actual/passed/error/latency 仍保留；页面与导出中 trace 链接显示“Trace 已过期”，不得报错或丢结果行。
