# 批量评测：问题、标准答案、通过率与 badcase

本实现以当前 V2 多动作识别链路为准；原 TASK-301 只作为参考。入口为后台“批量评测”（`/evaluation`）。

## 使用流程

1. 下载 `assets/AI_Coach_批量评测模板.xlsx`，或在“评测集与标准答案”中页面填写。
2. 主表只必填“问题”和“标准答案”。标准答案用业务语言描述动作、参数、先后关系、风险和追问。
3. 可选填写场景标签、关键用例及精确检查字段。复合意图通过可选动作、参数工作表表达；页面也提供动作卡片编辑器。
4. 保存评测集版本。编辑已有评测集始终保存新版本，不修改历史标准答案。
5. 新建任务，选择业务配置、识别模型、可选评审模型、重复次数、并发数和验收目标通过率。
6. Worker 后台执行。关闭页面后可通过任务列表或任务链接返回。
7. 查看“最终通过率”；有待复核、未执行或运行中记录时，显示当前通过率和“验收未完成”。
8. 一键筛选 badcase、按问题类别或场景筛选，对照问题、标准答案、实际结果与具体理由；导出筛选结果或创建子集复测。

模板只接受当前列定义。上下文通常留空，高级用例可在“上下文（可选）”填写 context JSON 对象。
Route 接受 name/zh，Intent 接受 name/zh/aliases，导入时按当前已发布配置解析为唯一名称。
非唯一匹配、Route/Intent 归属矛盾均阻止导入，不保留旧训练业务豁免规则。
参数名称和枚举值使用标准名称/值。最多 500 条用例，单用例最多 12 个期望动作。

## 判定口径

- 未标注表示不检查，明确 `无` 才表示要求为空。
- 精确检查动作数量、Route、Intent、参数、多余参数、组合方式、依赖、风险和追问触发。
- 并行/备选按最小差异一对一匹配；顺序动作按 order 对齐，依赖按对齐后的编号核对。
- 一个实际动作不能匹配多个期望动作。参数按 `(name, value)` 多重集合精确比较，不比较置信度和展示名称。
- 精确规则不符合即 FAIL，模型和人工不能覆盖；标准有误需要修订评测集新版本。
- 规则无错误后，由所选评审模型评审自然语言标准答案，输出 PASS/FAIL/REVIEW，并保存理由、标签和调用依据。
- 未选评审模型时由人工复核，不能把“规则没有发现错误”当作业务已通过。
- 评审失败、格式无效或语义不明确进入 REVIEW，不悄悄重跑直到通过。
- 评审 Prompt 固定并随任务保存，将问题、标准答案、实际结果作为数据，不执行其中的评分操纵指令。
- 人工修正语义评审需要复核人和理由，通过 revision 防止覆盖。自动结论不改写，复核追加历史。

本版一个自然语言标准答案配一套可选精确规则。多个可接受的业务表述可写入标准答案，由模型/人工评审；没有另建多套结构化答案分支。

## 通过率与验收

`通过率 = repeat_index=0 最终通过用例数 / 本任务全部用例数 × 100%`。

- ERROR、未执行、待复核都不从分母消失。
- repeat 1/3/5 不改变用例权重，额外重复用于通过次数和稳定性。
- 稳定性比较归一化动作、参数、组合方式、依赖、风险和追问触发；忽略置信度、展示名、生成编号和追问措辞。执行错误不能算稳定。
- 执行结束不等于验收通过。所有执行和复核完成后才形成最终结论。
- 验收达标要求达到创建时冻结的目标通过率，且关键用例所有重复均通过。
- 默认目标 100%，创建时可按业务要求调整；该默认值不是对模型效果的承诺。
- 普通用例额外重复失败显示在逐条结果中，主通过率仍取首次；关键用例任意重复失败会阻止达标。
- Avg/P95 是首次执行的服务端识别端到端耗时，包含等待、重试、Trace 保存，不含独立评审耗时。
- Route/Intent/参数等指标只统计显式标注。缺动作和执行错误算未识别，多动作增加误识别。
- Macro-F1 对期望样本数大于零的已标注 Route 取平均。没有标注的指标显示不适用。
- Token 仅展示已记录值，Provider 不返回 usage 时不推断账单。

直接对比要求相同数据集内容 hash 和规则版本，展示 PASS→FAIL/ERROR 退步及反向改善。
评审模型/参数变化会明确提示，代码摘要同时保留供追溯。
badcase 子集复测的分母是子集大小，不能与原完整集通过率直接比较。

导出包含原始用例、可选结构化标准、逐次结果、复核记录和任务概览。筛选不改变任务总通过率。
超长实际结果/复核历史拆分到“完整结果分段”表；文本单元格不执行公式。

## 持久化与恢复

沿用 evaluation_dataset、evaluation_run、evaluation_case_result，不引入 Redis/MQ。
任务冻结业务快照、识别/评审模型快照、凭据密文摘要、用例内容、判定 Prompt/版本、代码摘要、repeat 和并发。
不保存明文凭据。修改默认模型、enabled、业务发布、模型参数不影响已有任务。
凭据实际变化时停止任务并要求新建；代码变化后不混跑旧任务。

Worker 用 MySQL `FOR UPDATE SKIP LOCKED` 每次领取一个 Run，唯一领取 token 与 heartbeat 阻止旧 Worker 提交。
租约默认 60 秒，每 20 秒续租。失联任务由其他 Worker 恢复。结果唯一键为 `(run_id, case_id, repeat_index)`。
识别结果先持久化再评审；已保存的识别结果恢复时只继续评审。
模型返回但结果尚未落库时发生崩溃，恢复可能重复模型调用，不宣称外部调用 exactly-once。

每次识别独立捕获自己的 Trace，不查询“最新 Trace”。Trace 过期后结果仍完整保留。
取消停止新 Case 派发，正在执行的 Case 收尾。SIGTERM 停止派发并等待当前请求，强制中断依靠租约恢复。
Worker 独立于 API 进程。并发是任务、Worker 配置、冻结模型上限的最小值；多 Worker 总额度需要部署侧规划。

## 安装、迁移和启动

在 backend 目录执行，API 和 Worker 使用相同数据库与凭据加密密钥：

```powershell
uv sync --locked --extra dev
uv run --locked alembic upgrade head
uv run --locked python -m app.services.evaluation.worker
```

API 和前端沿用既有启动方式。本次开发未执行数据库迁移、启动 Worker 或真实模型调用。

`0006_evaluation_v2` 清空旧评测集、任务和结果，增加 V2 评测字段，不兼容旧评测语义；不删除业务配置、模型或 Trace。
更早的 `0005` 有独立的破坏性语义，从更早版本升级时不能把它与只执行 0006 混同。

| 环境变量 | 默认 | 用途 |
|---|---|---|
| EVAL_WORKER_CONCURRENCY | 4 | 每 Worker 并发上限 |
| EVAL_WORKER_POLL_SECONDS | 2 | 空闲领取间隔 |
| EVAL_WORKER_LEASE_SECONDS | 60 | 失联恢复时间 |

模板再生成：`uv run --locked python scripts/generate_evaluation_template.py`，只生成文件，不连接数据库/模型。
