# 08 部署与主系统接入设计

## 1. 已知环境

- 主系统：Java 微服务
- Intent：独立 Python/FastAPI 项目
- Frontend：Vue
- DB：MySQL 8 独立资源
- Deployment：Kubernetes
- Device/Main System：HTTP
- 暴露：接现有 Gateway/Ingress

## 2. 部署单元

- `intent-api` Deployment：Runtime API + Admin API（**不运行** Evaluation Worker loop）
- `intent-worker` Deployment：Evaluation Worker（与 intent-api 共用同一个 backend 镜像，仅启动命令不同）
- `intent-web` Deployment/Static Server：Vue Admin
- `intent-trace-cleanup` CronJob：按 `TRACE_RETENTION_DAYS` / `EVAL_TRACE_RETENTION_DAYS` 清理 Trace

起步副本：intent-api=2、intent-worker=1。Worker 必须通过 DB claim 保证多副本不会重复执行同一个 Run。
Runtime 与 Evaluation 不得共进程，避免批量评测抢占线上请求的 Provider 并发与 API 资源。

## 3. Runtime/Admin 网络边界

生产必须明确两条入口：

### 业务/设备入口

只允许：

- `/api/v1/intent/*`
- 必要的 `/health` / `/ready`（按平台规范）

不得把 `/api/admin/*` wildcard 暴露到设备/业务路由。

### 研发 Admin 入口

- Admin Web
- `/api/admin/*`

通过内部 Ingress/VPN/研发网段/平台已有鉴权之一限制访问。由于已有网络边界，一期可不自建用户账号体系。

E2E 必须验证：从业务入口请求 `/api/admin/*` 得到不可达/403/404。

## 4. K8s 基础要求

- backend/frontend Dockerfile
- Deployment/Service
- ConfigMap/Secret reference
- readinessProbe/livenessProbe
- requests/limits
- rollingUpdate
- terminationGracePeriodSeconds
- SIGTERM graceful shutdown
- replicas 可配置

Kubernetes `readinessProbe` 使用 `/ready`，只检查：进程可服务、DB/基础依赖可用、Migration schema 可用；**不得依赖 Active Release/default Model Config**。否则首次上线或配置损坏时 Pod 会被摘出 Service，Admin 无法完成导入/修复，形成配置死锁。

Runtime 配置就绪状态由 `/api/admin/status/summary.runtime_config_ready` 表示：Active Release 存在且 default Model Config 完整可加载时为 true；未就绪时 Runtime analyze 返回 `CONFIG_NOT_READY`。

## 5. 多 Pod 配置一致性

不依赖 Redis pub/sub。Runtime Config Loader 使用：

- active release id 轻量查询/短 TTL
- Snapshot 本地 cache
- TTL 到期后校验 active id

发布后允许一个短的、明确可配置的收敛窗口。

## 6. Evaluation 多 Pod

Worker 使用 MySQL claim；推荐 `SELECT ... FOR UPDATE SKIP LOCKED` 或等价事务方案。Run/Case result 幂等。

## 7. 外部变量

- DB URL/user/password
- Qwen/OpenAI-compatible base URL
- API key Secret
- runtime cache TTL
- provider concurrency defaults
- evaluation worker concurrency
- Admin allowed origins
- log level
- `MAX_TEXT_CHARS` / `MAX_CONTEXT_BYTES` / `MAX_REQUEST_BODY_BYTES` / `MAX_EVAL_FILE_BYTES` / `MAX_EVAL_CASES`（默认 500）/ `PROVIDER_QUEUE_WAIT_TIMEOUT`
- `TRACE_RETENTION_DAYS` / `EVAL_TRACE_RETENTION_DAYS` / `TRACE_RAW_MAX_BYTES`

Secret 不写入 repo/DB snapshot/Trace。

## 8. 首次上线

1. 部署 MySQL/创建 database。
2. 运行 Alembic migration。
3. 部署 intent-api/web，验证 `/ready` 已 ready，确保 Admin 修复入口可用。
4. 导入 bootstrap draft。
5. 创建 Model Config。
6. 发布首个 Release。
7. 验证 `/api/admin/status/summary.runtime_config_ready=true`，并用 Runtime smoke 验证不再返回 `CONFIG_NOT_READY`。
8. 接测试业务 Gateway Runtime path。
9. 验证 Admin path 仅研发入口可访问。
10. 运行 Smoke + E2E + 小规模 Evaluation。

## 9. 日志与监控

- 普通服务日志输出 stdout/stderr，交给现有 K8s 日志系统。
- Intent 调试 Trace 存 MySQL。
- 服务状态页只做研发摘要，不替代平台级监控。

## 10. Trace Cleanup 与日志边界

- 提供 Trace cleanup CLI/Job，可按 `TRACE_RETENTION_DAYS` 删除过期 request + attempts。
- 生产推荐 Kubernetes CronJob 定时执行。
- stdout/stderr 默认仅记录 request_id/trace_id/route/status/latency/error_code 等摘要，不打印完整用户文本、Final Prompt、Raw Response。
- Raw Trace 只通过内部 Admin 入口查看。

## 11. Admin 入口落地要求

生产 manifest/overlay 必须实际生成独立的内部 Admin 路由，且业务 ingress/gateway 只允许 `/api/v1/intent/*`。不得在最终部署文档中只写“Internal Ingress/VPN/CIDR/Gateway 鉴权任选一种”而不落地。若平台尚未提供专用鉴权，参考实现采用独立 internal ingress/service 且不配置公网负载均衡；环境 overlay 再补企业网络限制。

## 12. TASK-401 开工前必须确认的部署决策

| 决策项 | 默认方案（未确认时 Codex 按此落地） | 确认人 |
|---|---|---|
| Admin 入口方式 | 独立 internal Ingress + 独立 Service，不配置公网 LB；环境 overlay 再叠加企业网段/VPN/网关鉴权 | 运维/平台 |
| 业务网关放行路径 | 仅 `/api/v1/intent/*`（及按平台规范的 `/health`、`/ready`） | 平台网关负责人 |
| MySQL 实例/库名/账号 | 由环境 Secret 提供，不入库不入 repo | 运维 |
| Qwen 模型与 base_url | 以首个 Model Config 创建时选定为准 | 研发 |
| 初始副本数 | intent-api=2、intent-worker=1 | 研发/运维 |

默认方案不阻塞开发；TASK-401 启动前由研发在 `PROJECT_STATUS.md` 备注“已确认/沿用默认”。
